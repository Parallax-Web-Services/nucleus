# NEBULA foundation source kit

This is a reviewed-source refactor checkpoint, not a public installer or a production-ready generic Kubernetes product. It covers one private Ubuntu 24.04 Noble amd64 control-plane VM on libvirt/KVM. It does not provide HA, ARM64, automatic worker enrollment or five-node Kubernetes. No source in this package has been used to mutate a live host or guest during this refactor.

The five exact Alpha helper snapshots live under `reference/alpha-20261102/*.reference`. They preserve provenance, including historical host assumptions, but are never imported by the active loader. The four public package/image/CNI dependencies retain their byte pins. No private plan, ledger, session, keys, kubeconfig, logs, live inventory, downloaded binary or VM image is included.

Active APIs require a `FoundationContext`: a separately trusted source-manifest SHA256, the one versioned profile and explicit validated operator-local inputs. There are no implicit host, developer checkout, temporary helper, credential, process ID or SSH target defaults. Resource/platform/API/CIDR policy is deliberately limited to the first reviewed profile. Safe state roots must be distinct named children of `/var/lib/nebula-foundation/`; run and guest identities are explicit/captured, never discovered from private sessions. Plans bind the manifest/profile/input identity privately.

The single loader verifies the complete manifest inventory, file hashes, nofollow same-buffer custody and within-context file identity. Dependency source is loaded only through declared logical names. The public signed-package verifier is a script artifact, not an importable module: importing bootstrap never runs signature tools or parses operational arguments. All source edits require regenerating and independently reviewing the candidate manifest; generation is not approval.

Host/guest `run_phase` APIs retain explicit execution gates, private operation locks, source/resource/object guards and known-state failure handling. Recovery remains separate and evidence-gated; there is no automatic reset/delete/rekey/retry. These developer APIs have not received disposable-host/guest acceptance. The safe health adapter takes explicit in-memory transport/proof callbacks and publishes only bounded safe summary fields; actual SSH/credential/session adapters are intentionally absent.

Read-only inspection from the repository root (replace the pin with the separately reviewed candidate SHA):

```sh
PYTHONPATH=tools python3 -B -m foundation verify --manifest-sha256 REVIEWED_SHA256
PYTHONPATH=tools python3 -B -m foundation profile --manifest-sha256 REVIEWED_SHA256
```

Use `-B`/`PYTHONDONTWRITEBYTECODE=1`; generated bytecode is not part of the reviewed inventory. For a development candidate only, run `PYTHONPATH=tools python3 -B tools/foundation/build_manifest.py` and save its stdout as `source-manifest.json`, then review the complete change and pin. Never derive a trust pin from an unreviewed package during production use.

Offline fixtures run from `tools/foundation` with `PYTHONPATH=.. PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s tests -v`. Linux root is needed for the inherited private-ownership cases; all fixture targets are synthetic and freshly created. Libvirt, SSH, systemd, package/signature commands and network transports are mocked. Strict archive fixtures are generated locally; real runtime/package/image artifacts are deliberately absent and their acceptance is not claimed. See `MIGRATION.md` for retained cases and remaining limits.
