# Distributed model execution: research only

Production Nucleus distributes independent requests; it never enables llama.cpp RPC. The upstream [RPC README](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md) describes remote CPU/accelerator devices, tensor/KV placement, caching and optional RDMA. Upstream labels the implementation experimental and insecure. It is unsuitable for the current private-data execution path without additional security work.

Engineering estimates to test, not measurements: a cold start needs roughly model tensor bytes divided by effective link throughput in addition to loading/allocation time. A 4 GiB transfer has a theoretical wire-time floor of about 34 seconds at 1 Gb/s before protocol overhead. A layer boundary sends activations whose approximate size scales with batch tokens times hidden width times element bytes; graph execution may exchange additional tensors and incur multiple round trips. Decode is sequential across dependencies, so extra nodes do not automatically reduce individual-request latency.

Weights, KV caches, activation/scratch buffers and coordinator overhead must all fit their placement budgets. Layer partitioning could help when a model cannot fit one node, or when saved compute time exceeds transfer, synchronization and straggler costs on a fast low-latency fabric. Memory capacity aggregation and request-throughput aggregation are different from faster token latency. TCP/LAN, Wi-Fi and cross-site links require separate measurement; no performance claim is made here.

A research feature would require a default-off build/config gate, pinned compatible versions, authenticated encrypted transport around every endpoint, revocation, resource limits, provenance and no public RPC listener. Compare single-node CPU, independent-request distribution and partitioned execution using the same model/quantization/context, measured startup/prefill/decode/RSS/network bytes and p50/p95 latency. Include disconnect, corrupted-worker and slow-link cases. Other candidates are pipeline/layer partitioning or tensor-parallel runtimes behind the same backend interface, each subject to these tests. Do not deploy any partitioning path until its security boundary and benefit are demonstrated.
